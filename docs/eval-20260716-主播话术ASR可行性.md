# 主播话术文字（ASR）可行性验证

**日期**：2026-07-16
**结论**：技术上完全走得通，本地免费方案（funasr）识别质量够用。是四项诉求里最重的一块，建议想做时单独立项。

---

## 一、背景

看板已交付「商品讲解联动」。用户提出的第四项诉求是把**主播话术转成文字**，和弹幕/VOC/商品讲解做联动分析。本文档记录对这一块的可行性实测评估，供后续决策，暂不进入开发。

## 二、可行性结论（都有实测证据）

| 环节 | 结论 | 实测证据 |
|---|---|---|
| 直播流地址 | 可拿 | 播放器现请求的签名 flv 地址，备源 Playwright 页面能从 network 抓到（`stream-..._ld.flv?expire=&sign=` / `?auth_key=`） |
| 拉流 | 可拉 | 浏览器上下文拉不 403，流持续在传（直接 GET 超时是无限流特性，非被拒）。ffmpeg 流式拉 40 秒成功抽出 16k 单声道音频 |
| 音频→文字 | 质量优秀 | funasr paraformer-zh 转写，带货话术完整准确、带标点、扛得住 BGM |
| 速度 | CPU 可实时 | 离线整段 RTF=0.07（40 秒音频推理 2.8 秒），一个核能同时扛多路 |

### 实测转写样本（BKT 护腰坐垫直播，40 秒，含背景音乐）

> 拿去车上主驾副驾，你这么坐着，你看你开车人又是很舒服。然后回家你可以拎着他，你到地下车库直接拿楼上去了，是不是在家里沙发上床上？……假如我工作没办完，我拿去书房，我继续工作，是不是人也舒适？然后我累了，我打会儿游戏，我去我的电竞椅上打会游戏坐着……我今天我朋友约我去打个麻将，我拎着他要去打麻将，打六七个小时，我都能坐得住。因为他对我的腰很有帮助啊，我坐久坐不累呀。

之前担心的「BGM 干扰、带货口语转不准」实测没问题。句读正确、推销逻辑连贯。

## 三、技术方案（真做时的实时管线）

1. **采集**：备源 Playwright 页面抓播放器现请求的签名 flv 地址（复用现有 network 监听）。签名过期要重抓，断流要重连。
2. **抽音频**：ffmpeg 流式拉 flv，抽音频，按 VAD 或固定窗口切段。
3. **转写**：funasr 流式分段转文字，带时间戳存库。
4. **联动**：转写文本按时间戳与弹幕/商品讲解时间轴对齐。

## 四、ASR 选型（中文带货场景）

| 方案 | 优 | 劣 |
|---|---|---|
| **本地 funasr**（已验证）| 中文最强、免费、不联网 | 吃 CPU/内存，有 GPU 更流畅；磁盘占用大 |
| faster-whisper | CPU 友好 | 直播口语/专业词识别一般 |
| 云实时 ASR（讯飞/阿里/腾讯）| 中文带货术语准、省心 | 约 ¥2-4/小时/路，要联网+密钥 |

**已选**：本地 funasr（用户定：免费但吃机器，适合少路监控）。

## 五、成本

- **计算**：一路直播实时转写，本地 CPU funasr 实时率有富余（离线 RTF=0.07，流式会高些但稳在 1 以下）。多路需 GPU 或走云。
- **磁盘**：torch + torchaudio + funasr + 3 个模型（paraformer 约 1GB + fsmn-vad + ct-punc）≈ 3-4GB。
- **首次部署**：模型从 modelscope 下载约 20 分钟（一次性，网络慢）。打包 exe 需一并塞模型或首次运行时下载。
- **工程**：比商品那块重。重在流式拉取 + 分段 + 转写 + 对齐整条管线，以及断流重连、签名过期重抓、背景音乐/BGM 降噪。

## 六、价值与呈现

价值高，但 ROI 低于商品联动（商品是轻量接口调用，话术是重管线+持续算力）。真正值钱的用法：

- **话术合规扫描**：话术命中极限词/违禁词（「最」「第一」「国家级」「根治」）标红——带货合规刚需。
- **话术×商品**：每个商品讲解段落配主播当时话术（商品面板点开看这个品讲了什么）。
- **话术×弹幕对齐**：某句话术后弹幕/在线怎么变。
- **话术流**：带时间戳的转写文本，像弹幕流一样滚动。

## 七、坑与注意

- funasr 依赖 torch + torchaudio（CPU 版），且安装会把 **protobuf 升到 7.x**、连带升 transformers 等。已验证升级后 douyin 项目的 proto 解析和 17 个测试照常（protobuf roundtrip OK）。真做时若打进同一环境，注意 protobuf 版本别和现有 proto 生成代码冲突。
- 本地 ffmpeg 环境原本没有，用 `imageio-ffmpeg`（静态二进制约 30MB）解决；打包时体积再 +30~80MB。
- RTF=0.07 是离线整段推理；实时流式模式 RTF 会高一些，但仍可实时。
- 直播流签名（expire/sign/auth_key）有时效，长时间采集要周期性重抓地址；连接建立后流可持续，但断流要重连。

## 八、建议

- 技术验证已过，识别质量够用，随时可做。
- 但它是四项里最重的：重在**持续算力 + ffmpeg/ASR 依赖 + 断流/签名/降噪工程**，不该和现在这套混在一个进程里。**建议单独立项**（独立采集进程 + 独立算力预算）。
- 真做时的第一步：把本文档的实时管线搭起来，先跑通「一路直播 → 实时话术流」，再接合规扫描和商品/弹幕对齐。
