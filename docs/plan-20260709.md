# 实现计划 — 抖音直播间实时弹幕采集与看板

日期:2026-07-09
形态:Windows 本机运行,浏览器呈现,先做单直播间。

---

## 一、架构总览

单一采集进程 + 本地 Web 服务 + 浏览器前端,全部跑在用户本机。

```
抖音直播间
   │  (1) 抓页面拿 room_id / ttwid
   ▼
[采集内核 collector]  Python
   │  (2) 用抖音官方 webmssdk.js 算签名
   │  (3) 连抖音 IM WebSocket,发心跳/回 ack
   │  (4) protobuf 解帧 + gzip 解压 → 消息对象
   ├──────────────► (5) 写入 SQLite(持久化)
   └──────────────► (6) 广播到本地服务
                          │
                   [本地服务 server]  FastAPI + uvicorn
                          │  WebSocket 推送 + 聚合接口
                          ▼
                   [浏览器前端]  静态 HTML/JS
                     ├─ 实时弹幕流页
                     └─ 实时看板页(图表)
```

打包:PyInstaller 打成单个 exe,双击启动后自动拉起本地服务并打开浏览器。

---

## 二、技术栈定稿

| 层 | 选型 | 理由 |
|----|------|------|
| 采集 | Python + requests + websocket-client + protobuf | 生态全,协议处理成熟 |
| 签名 | mini-racer(嵌入 V8 执行 webmssdk.js) | 纯 Python 内嵌 JS 引擎,免装 Node,利于打包 |
| 存储 | SQLite(标准库 sqlite3) | 单机零配置,单文件数据库,最适合 Win 单机程序 |
| 服务 | FastAPI + uvicorn | WebSocket 支持好,轻量,能同时供静态页和实时推送 |
| 前端 | 原生 HTML/CSS/JS + 轻量图表库 | 无重框架,打包体积小;弹幕流和图表 Web 表现最佳 |
| 打包 | PyInstaller | 主流 Win 打包方案,产出单 exe |

## 三、模块拆解与实现顺序

依赖顺序从上到下,每个模块都能独立验证。

**M1 直播间信息抓取**(已起步,`src/fetch_room.py`)
- 现状:能拿到 ttwid;room_id 解析当前未命中,待修
- 待办:换用更稳的解析法(定位页面里嵌的 room 数据 JSON),用一个正在直播的房间实测通过

**M2 签名生成**(硬骨头)
- 从直播间页面提取抖音官方 `webmssdk.js`
- 用 mini-racer 补最小浏览器环境(window/document/navigator shim)后执行
- 调用其签名函数,输入 room_id / user_unique_id 等,拿到 wss 所需 signature
- 验证:签名能让 WebSocket 握手被抖音接受
- 兜底:若补环境代价过高,临时用 Playwright 浏览器方案隔离验证协议其余部分

**M3 WebSocket 连接**
- 用 M1、M2 的产物拼 wss URL,建长连接
- 实现心跳定时发送、按 needAck 回 ack
- 验证:连接能稳定维持 5 分钟以上不断线

**M4 protobuf 消息解析**
- 自己写 `douyin.proto`(字段定义是抖音协议事实):PushFrame、Response、以及 ChatMessage / GiftMessage / LikeMessage / MemberMessage / RoomUserSeqMessage
- 生成 Python 代码,解帧:PushFrame → gzip 解压 → Response → 按 method 分发
- 验证:终端能实时打印真实弹幕文本 + 发送人昵称

**M5 存储**
- SQLite 建表(见下方数据模型),消息对象逐条写入
- 验证:弹幕入库,能 SQL 查出来

**M6 本地服务 + 前端**
- FastAPI:静态页托管 + WebSocket 广播实时消息 + 看板聚合接口
- 前端弹幕流页:接 WebSocket,新弹幕滚动追加
- 前端看板页:图表实时更新(指标见下)
- 验证:浏览器同时看到实时滚动的弹幕流和动态更新的看板

**M7 打包**
- PyInstaller 打单 exe,内置前端静态资源和 webmssdk.js
- 启动自动开浏览器指向本地端口
- 验证:干净的 Win 机器上双击 exe 能跑起来

## 四、数据模型(SQLite)

- `danmu` 弹幕:id, room_id, msg_id, user_id, nickname, gender, content, ts, created_at
- `gift` 礼物:id, room_id, user_id, nickname, gift_name, gift_count, diamond, ts, created_at
- `enter` 进场:id, room_id, user_id, nickname, ts, created_at
- `like` 点赞:id, room_id, user_id, nickname, count, ts, created_at
- `room_stat` 在线快照:id, room_id, online_count, total_user, ts, created_at

`ts` 为消息时间,`created_at` 为入库时间。按 room_id + ts 建索引。

## 五、看板指标(单房间)

- 数字卡:累计弹幕数、累计礼物数、累计点赞数、当前在线人数
- 折线:在线人数走势、弹幕速率(每分钟弹幕条数)
- 排行:礼物榜(按钻石数)、活跃用户榜(按发言数)
- 热词:弹幕分词后的高频词(条形或词云)

## 六、里程碑

- **阶段一 · 采集内核打通**(M1修复 + M2 + M3 + M4):终端能实时打印真实弹幕。这是可行性从"理论"落到"实测"的关键节点。
- **阶段二 · 存储**(M5):弹幕持久化入库,可查询。
- **阶段三 · 呈现**(M6):浏览器看到实时弹幕流 + 基础看板。
- **阶段四 · 成品**(M7):打包 exe,双击运行。

---

## 七、风险与应对

- **签名(M2)是最大不确定性**:webmssdk.js 的提取和补环境有工程量,且抖音更新算法时需跟进。应对:先 mini-racer 执行;卡住则用 Playwright 浏览器方案兜底,不阻塞其余模块。
- **M1 room_id 抓取当前未通**:需要一个正在直播的房间实测,并可能调整解析法(数据在页面内嵌 JSON 里)。
- **protobuf 字段对齐(M4)**:字段编号需对上抖音,靠协议事实校准,解不出可读文本就说明字段没对齐。

## 八、测试策略

## 九、实现方式说明

采集内核(M1到M4)强依赖对抖音实时响应的反复调试(签名是否被接受、字段是否对齐、连接是否维持),属于边跑边调的迭代实现,由本体主导逐模块落地,每模块实测通过再进下一个,不做黑盒外包。前端看板(M6)相对独立,届时视情况决定是否并行分工。
